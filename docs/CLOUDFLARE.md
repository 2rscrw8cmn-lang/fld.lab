# fld.LAB — Cloudflare + D1 Runbook

This document defines how fld.LAB should be created, configured, migrated, developed, deployed, and recovered on Cloudflare.

Use this as the operational source of truth for Cloudflare setup. The product and data architecture remain defined in `PRODUCT.md`, `DATA_MODEL.md`, and `TECHNICAL.md`.

---

## 1. Platform decision

fld.LAB should use one Cloudflare deployment unit:

```text
React + TypeScript + Vite
        │
Cloudflare Static Assets
        │
Cloudflare Worker API
        │
Cloudflare D1
```

Do not split the front end and API into separate hosting platforms unless a concrete requirement appears.

Primary services:
- Cloudflare Workers
- Cloudflare Static Assets
- Cloudflare D1
- Wrangler
- Cloudflare Vite plugin

Optional later:
- R2 for uploaded/exported files
- Access or another auth layer if access control requirements grow

---

## 2. Naming conventions

Use these names unless there is a strong reason to change them during setup.

### Worker

```text
fld-lab
```

### Production D1 database

```text
fld-lab-prod
```

### D1 binding name

```text
DB
```

Worker code should access the database through:

```ts
env.DB
```

Do not embed D1 database IDs in application code. IDs belong in Wrangler configuration.

---

## 3. Project creation

For a new Cloudflare React application, prefer the current Cloudflare React + Vite scaffold rather than manually assembling the Worker integration.

Typical scaffold command:

```bash
npm create cloudflare@latest -- fld-lab --framework=react
```

When scaffolding inside an existing repository, preserve the existing docs and Git history rather than replacing the repository.

The expected high-level structure is:

```text
/
├── docs/
├── migrations/
├── public/
├── src/
├── worker/
│   └── index.ts
├── vite.config.ts
├── wrangler.jsonc
└── package.json
```

Exact generated structure may vary by Cloudflare tooling version. Keep the architectural intent rather than forcing an obsolete file layout.

## 4. Wrangler configuration

The production repository should contain `wrangler.jsonc`.

Representative configuration:

```jsonc
{
  "$schema": "node_modules/wrangler/config-schema.json",
  "name": "fld-lab",
  "main": "worker/index.ts",
  "compatibility_date": "YYYY-MM-DD",
  "assets": {
    "not_found_handling": "single-page-application"
  },
  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "fld-lab-prod",
      "database_id": "<D1_DATABASE_ID>",
      "migrations_dir": "migrations"
    }
  ]
}
```

Important:
- Use the compatibility date produced/expected by the current scaffold when Issue #1 is implemented.
- `main` must point to the actual Worker entry generated by the chosen scaffold.
- Do not copy placeholder database IDs into production.
- SPA fallback should remain enabled for client-side application routes.

If Cloudflare's current scaffold generates materially different valid configuration, keep the generated shape and preserve the same binding and migration rules.

---

## 5. Create the production D1 database

Create the remote database once:

```bash
npx wrangler d1 create fld-lab-prod
```

Wrangler returns the D1 database ID and binding configuration.

Copy the real `database_id` into `wrangler.jsonc` under the `DB` binding.

Do not create a new production database for every deployment.

---

## 6. Local development database

Local development should use Wrangler's local D1 emulation.

The local database is separate from production data.

Apply migrations locally:

```bash
npx wrangler d1 migrations apply fld-lab-prod --local
```

Start the application using the project's normal development script, expected to be:

```bash
npm run dev
```

Local development should never require connecting to production D1 for normal feature work.

### Local persistence

Wrangler persists local D1 state across development runs by default with current tooling.

If a custom persistence directory becomes necessary:

```bash
npx wrangler dev --persist-to=.wrangler/local-state
```

Do not commit local D1 state files.

---

## 7. Migrations

All schema changes must be migrations.

Never manually edit the production database schema through the dashboard as the normal development workflow.

### Create a migration

```bash
npx wrangler d1 migrations create fld-lab-prod create_athletes
```

Expected result:

```text
migrations/
└── 0001_create_athletes.sql
```

Migration names should describe the schema change.

Good:

```text
0001_initial_schema.sql
0002_add_athlete_status.sql
0003_add_session_indexes.sql
```

Bad:

```text
0002_changes.sql
0003_fix.sql
```

### Apply locally first

```bash
npx wrangler d1 migrations apply fld-lab-prod --local
```

Run the application and tests before applying the migration remotely.

### Review unapplied migrations

Local:

```bash
npx wrangler d1 migrations list fld-lab-prod --local
```

Production:

```bash
npx wrangler d1 migrations list fld-lab-prod --remote
```

### Apply to production

```bash
npx wrangler d1 migrations apply fld-lab-prod --remote
```

Production migrations should normally be applied as part of a deliberate deployment step, not casually while developing.

## 8. Initial migration strategy

Phase 1 should establish only the tables required for the current scope.

Start with:

```text
teams
athletes
team_athletes / team membership relationship as defined by DATA_MODEL.md
```

Later phases add:

```text
drills
drill_versions
sessions
attempts
measurements
splits
```

Do not create speculative tables for messaging, parents, attendance, payments, medical data, or other post-MVP systems.

---

## 9. Database indexes

Indexes should be introduced in migrations alongside the queries that need them.

Likely indexes include:

```text
athletes(active/status)
team-athlete relationship by team_id
sessions(team_id, started_at)
attempts(session_id)
attempts(athlete_id)
attempts(drill_version_id)
measurements(attempt_id)
splits(attempt_id)
```

Exact names should follow the final table design.

Do not add indexes blindly. Add them for real access patterns and keep migrations explicit.

---

## 10. D1 data rules

These rules are mandatory:

- Use stable generated IDs.
- Never use athlete names, jersey numbers, or drill names as primary keys.
- Store timed values as integer milliseconds.
- Store timestamps consistently.
- Use migrations for every schema change.
- Archive historical entities where deletion would break history.
- Drill versions become immutable once referenced by recorded results.
- Historical attempt records should continue to point to the exact drill version used at capture time.
- Do not silently cascade-delete athlete performance history.

Refer to `DATA_MODEL.md` for table-level details.

---

## 11. Seed data

Development seed data is allowed and encouraged.

Keep seed data separate from schema migrations when practical.

Suggested development seed content:
- one sample U10 team
- 8–12 fictional athletes
- starter drills such as 10-Yard Sprint, 20-Yard Sprint, 5-10-5 Shuttle, Catching, Flag Pull, and QB Accuracy
- several sample results for chart development

Never seed production with fake athlete records by default.

If a seed SQL file is used:

```text
scripts/
└── seed.local.sql
```

Example local execution:

```bash
npx wrangler d1 execute fld-lab-prod --local --file=./scripts/seed.local.sql
```

## 12. Local vs production rules

### Local

Use:

```text
--local
```

for development database operations.

Examples:

```bash
npx wrangler d1 migrations apply fld-lab-prod --local
npx wrangler d1 execute fld-lab-prod --local --command "SELECT * FROM athletes;"
```

### Production

Use:

```text
--remote
```

only when intentionally operating on Cloudflare-hosted D1.

Examples:

```bash
npx wrangler d1 migrations apply fld-lab-prod --remote
npx wrangler d1 execute fld-lab-prod --remote --command "SELECT COUNT(*) FROM athletes;"
```

Treat `--remote` commands as production operations.

Never use destructive remote SQL casually during debugging.

## 13. Preview environments

MVP does not require a separate preview database.

Recommended initial model:

```text
Local development → local D1
Production → fld-lab-prod
```

If multiple developers, automated preview deployments, or risky schema work make a preview database useful later, add:

```text
fld-lab-preview
```

and configure it explicitly rather than sharing production data with preview builds.

Do not block Phase 1 on preview infrastructure.

## 14. Secrets and environment variables

D1 bindings are not secrets and belong in Wrangler configuration.

Sensitive credentials must not be committed to Git.

### Local secrets

Use `.dev.vars` for local Worker secrets when secrets are eventually required:

```text
.dev.vars
```

Example:

```dotenv
EXAMPLE_API_TOKEN="local-value"
```

Add to `.gitignore`:

```gitignore
.dev.vars*
.env*
```

Do not use both `.dev.vars` and `.env` as competing secret sources in the same setup.

### Production secrets

Set production secrets with Wrangler:

```bash
npx wrangler secret put SECRET_NAME
```

For the first unauthenticated MVP, fld.LAB may require no application secrets at all.

Do not invent secret infrastructure before an actual secret exists.

## 15. Worker bindings and generated types

The Worker should receive D1 through the `DB` binding.

Conceptually:

```ts
export interface Env {
  DB: D1Database
}
```

Prefer Wrangler-generated binding types when the scaffold supports them.

Do not use `any` for the Worker environment just to bypass binding errors.

## 16. Deployment workflow

Phase 1 should end with a repeatable deployment flow.

Expected sequence:

```bash
npm install
npm run typecheck
npm test
npm run build
npx wrangler d1 migrations list fld-lab-prod --remote
npx wrangler d1 migrations apply fld-lab-prod --remote
npx wrangler deploy
```

Only keep commands that actually exist in `package.json`; if `typecheck` or `test` scripts have not yet been created, add them during the scaffold rather than documenting fake scripts indefinitely.

### Deployment rule

A deploy should never require manual database edits in the Cloudflare dashboard.

The repository must contain everything required to reproduce the application schema.

## 17. Database export

D1 can be exported to SQL.

Production export example:

```bash
npx wrangler d1 export fld-lab-prod --remote --output=./backups/fld-lab-prod.sql
```

Local export example:

```bash
npx wrangler d1 export fld-lab-prod --local --output=./backups/fld-lab-local.sql
```

Do not commit production database exports containing athlete data to the public repository.

If manual exports are kept, store them outside the repository or in an appropriately protected backup location.

---

## 18. Time Travel and recovery

D1 Time Travel should be the first-line recovery mechanism for accidental destructive changes or failed data operations.

Time Travel is managed by Cloudflare and supports point-in-time restoration within the retention window available to the account plan.

Recovery procedure after a serious production incident:

1. Stop making additional production writes if practical.
2. Identify the bad migration, delete, or update timestamp.
3. Inspect the available D1 Time Travel point/bookmark.
4. Restore only after confirming the target point.
5. Verify roster and result integrity.
6. Correct the code or migration before deploying again.

A restore is a production-changing operation and should be treated accordingly.

For long-term backups beyond Time Travel retention, use periodic protected exports later if the product reaches the point where that is warranted.

---

## 19. Data privacy

The repository is public, so production data must never be committed.

Do not commit:
- athlete exports
- database dumps
- access tokens
- Cloudflare API tokens
- `.dev.vars`
- real production seed files
- screenshots containing sensitive athlete information unless intentionally sanitized

Keep youth-athlete PII minimal as defined in `PRODUCT.md`.

---

## 20. Production database access

Application access to D1 must go through the Worker binding.

Browser code should never receive:
- Cloudflare API credentials
- D1 management credentials
- direct administrative database access

Normal architecture:

```text
Browser
  ↓ fetch /api/*
Worker
  ↓ env.DB
D1
```

The browser should not directly administer D1.

---

## 21. Failure behavior

Database or network failure must not affect stopwatch timing.

For training capture:

1. timing occurs locally in the browser
2. completed result enters local application state
3. coach advances to next athlete
4. Worker persists the result to D1
5. failed persistence remains visibly retryable

Never discard a completed athlete result because D1 or the network was temporarily unavailable.

See `TECHNICAL.md` for the full timing rules.

## 24. Implementation guardrails

- One production D1 database is enough for MVP.
- Do not use production D1 as the normal local development database.
- Do not hard-code database IDs in TypeScript.
- Do not add an ORM unless it clearly reduces complexity.
- Do not manually patch production schema outside migrations as a normal workflow.
- Do not expose D1 administration to the browser.
- Do not store production exports in the public repo.
- Do not let database writes block athlete switching or stopwatch timing.
- Do not create preview infrastructure until it is useful.
- Keep Cloudflare configuration reproducible from the repository.
